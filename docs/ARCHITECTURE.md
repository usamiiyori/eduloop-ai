# EduLoop AI — アーキテクチャ設計ドキュメント

「教育 × 生成AI 公的情報自律配信＆知見集約プラットフォーム」の設計根拠をまとめる。実装規約は `CLAUDE.md`、フェーズ計画は `docs/ROADMAP.md`、DBスキーマは `sql/` を参照。

## 0. コンセプト

公的機関・学術機関から教育・生成AIの一次情報を自律収集・検証・配信し、将来の教員コミュニティへ知見を循環させる。設計思想は **Human-on-the-Loop**: AIが収集から下書き生成・自動検証まで自律的に行うが、外部公開の最終ゲートは常に人間が握る。オーナーは実名で発信するため、速度よりも正確性を優先し、判断に迷ったら「出さない」を選ぶ。

## 1. 収集対象ソース（3軸・多階層）

## 2. 4層エンジニアリング仕様（Human-on-the-Loop）

```
[1. プロンプト層]   現場教員向け論点抽出 (Fact / Implication / Discussion / Citation)
        │
        ▼
[2. コンテキスト層] 学習指導要領、過去答申、自治体方針、編集ペルソナ、教員フィードバックの動的注入
        │
        ▼
[3. ハーネス層]     G1〜G6 の自動検証ゲート + 自己修復ループ（最大3回リトライ）
        │
        ▼
[4. ループ層]       L1(高速自動:数十分〜1時間) → L2(監督/承認:日次) → L3(知見還元:月次)
```

### 2.1 プロンプト層
収集した一次情報から、現場教員が意思決定・実践に使える形で論点を抽出する。抽出フォーマットは4観点固定:
- **Fact**: 原文に明記された事実・数値（出典行を必ず保持、数字の丸め・概算は禁止）
- **Implication**: 教育現場への含意（AIによる解釈である旨を明示）
- **Discussion**: 論点・賛否・未解決課題
- **Citation**: SIST02 準拠の出典情報

### 2.2 コンテキスト層
静的なプロンプトに終わらせず、以下を実行時に動的注入する:
- 学習指導要領・過去答申（Supabase の参照テーブル）
- 自治体方針（B軸ソースの既収集データ）
- 編集ペルソナ・文体規定（`config/editorial_voice.yaml`、第6章）
- 教員フィードバック（L3で蓄積された実践知・コメント）

コンテキストのハードコードは禁止。すべて DB 参照または直近収集データから構築する。

### 2.3 ハーネス層（G1〜G6 自動検証ゲート）
生成物は以下6ゲートを**全パス**しない限り公開フェーズ（L2レビューキューへの提示以降）に進めない。失敗時はエラーログを添えて**最大3回**自律リトライし、失敗ゲート名と理由をプロンプトに再注入する。3回失敗した場合は破棄せず `needs_human` ステータスで L2 キューに残す（Human-on-the-Loop の担保）。

| ゲート | 内容 | 実装方針 |
| --- | --- | --- |
| **G1 事実整合性** | 生成文中の事実主張・数値が原文中に実在するか | 主張を文単位に分解 → 原文への文字列一致＋埋め込み類似度のハイブリッド照合。閾値未満は該当箇所を指摘して再生成 |
| **G2 出典・ライセンス** | SIST02準拠の書誌情報＋Schema.org（NewsArticle/TechArticle）が完全か。第5章の再配布モードに違反していないか | 引用比率を機械計測。違反時はブロック |
| **G3 個人情報 (PII)** | 生徒名・教員個人名・特定可能な学校名・機微情報 | 正規表現＋モデレーション判定の二段。検出時は自動マスクせず**ブロックして人間に回す** |
| **G4 断定リスク（最重要）** | 政策文書の段階を誤読していないか | LLM-as-a-Judge で判定: 「検討中/中間まとめ/答申/告示/施行」の段階混同、原文で裏付けられない断定（「〜が決定した」「〜が義務化される」等）を検出。1つでも該当すれば差し戻し |
| **G5 重複・既報** | 過去出力と実質同一の内容を再投稿していないか | 過去記事の埋め込みとコサイン類似度比較。閾値超過は「続報」フォーマットへ強制切替 |
| **G6 構造** | Web記事Markdown / Xスレッド(140字×3〜5) / YouTube台本のスキーマ | Pydantic v2 で厳格バリデーション |

事実整合性・LLM-as-a-Judge 系の判定は、機械的な文字列照合（Citation Matching）を第一ゲートとし、曖昧なケースのみ LLM-as-a-Judge による二重検証に回す（コスト最適化とハルシネーション耐性の両立）。

### 2.4 ループ層（3段階運用サイクル）
- **L1（高速自動・数十分〜1時間間隔）**: 収集（scrapers）→下書き生成（processors）→自動検証（harness）まで完全自律。人間の介在なし。
- **L2（監督/承認・日次）**: メール（1日1回・夕方まとめて）が「レビューしてください」と通知し、人間はWeb承認画面（Supabase連携）で生成物をレビューして承認/差し戻し/却下を行う。承認されたものだけが `publishers/` に渡る。差し戻しは修正指示とともに L1 の再生成キューに戻す。
- **L3（知見還元・月次）**: 教員コミュニティからのコメント・実践報告・利用状況を集約し、A/B/C軸のソース優先度やコンテキスト層の教員フィードバックデータ、ネタ選定スコアリング（第7章）を更新する。収集→配信→還元の循環を閉じる。

## 3. インフラ・セキュリティ・データ基盤

- **言語・環境**: Python 3.11+ / Playwright / BeautifulSoup4 / Pydantic v2 / google-genai
- **実行基盤: GitHub Actions（cron）を既定とする。**
  - L1: GitHub Actions cron（毎時）→ scrapers → processors → harness
  - L2: Web承認画面での承認操作（Supabaseへの直接書き込み）をGitHub Actions（日次cron）が検知し、publishers を実行
  - L3: GitHub Actions cron（月次）→ 知見集約・スコアリング更新
  - 採用理由: オーナーはノーコード運用者である。GitHub Actions はシークレット管理・実行ログ閲覧・失敗時の再実行がすべてブラウザUIで完結し、追加課金設定も不要。Cloud Run + Eventarc + Cloud Scheduler + Secret Manager の構成は、障害時にオーナー単独で復旧できない。
  - **GCP移行が必要になる条件**（実行時間15分超、常時起動、大量並列のいずれかに該当した時点）を `docs/運用マニュアル.md` に明記し、その時点で移行判断できる形にしておく。
- **機密管理**: GitHub Actions Secrets（本番）/ `.env`（ローカル）。APIキー・クレデンシャルはコード内に含めず、`src/config.py` 経由で取得する。
- **データベース & 認証**: Supabase (PostgreSQL)
  - RLS (Row Level Security) による厳格なアクセス制御。テーブルごとにロール（`service_role` / `authenticated` / `anon`）別ポリシーを明示定義する。
  - 将来の教員ログイン認証、コメント投稿、実践知蓄積テーブルを初期スキーマから設計しておく（後付け拡張ではなく最初から想定）。

## 4. 収益モデルとKPI

オーナーのゴールは①X/YouTubeの収益化プログラム②noteの有料記事・メンバーシップ③業界内での知名度確立とキャリアアップ（最重要）。各施策の効果は推測せず、計測可能な形でDBに持たせる。

| レイヤー | 施策 | 計測すべき指標 | 必要なテーブル/実装 |
| --- | --- | --- | --- |
| 集客 | X スレッド、YouTube | インプレッション、プロフィールクリック | `post_metrics`（手動入力とAPI取得の両対応） |
| 回遊 | Web記事（自社サイト） | 流入元、滞在、記事別PV | UTMパラメータ自動付与、`link_clicks` |
| 収益 | note 有料 / メンバーシップ | 記事別コンバージョン | `conversions`（note経由は手動入力フォールバック必須） |
| 信用 | 引用・言及・登壇依頼 | 被言及数、問い合わせ数 | `inbound_leads`、問い合わせフォーム |

必須実装: すべての外部リンクへのUTM自動付与ユーティリティ／Web記事末尾への「note有料版導線」「問い合わせ導線」自動挿入テンプレート／問い合わせフォーム＋送信内容のDB保存。

## 5. 法務ゲート

**このシステムは文化庁の著作権WG資料をスクレイピングする。システム自体が著作権リスクを抱える構造である。** `config/sources.yaml` の各ソースに以下フィールドを必須とする（詳細は `CLAUDE.md` 第4章）。

```yaml
- id: mext_press
  name: 文部科学省 報道発表
  license: gov_standard_terms_2_0   # 政府標準利用規約(第2.0版) / CC-BY-4.0 / arxiv-varies / copyrighted-quote-only
  attribution_required: true
  redistribution: full_allowed      # full_allowed / summary_only / quote_only
  quote_max_ratio: null             # quote_only の場合は 0.1 など
```

再配布モードごとの生成ルールは G2 ゲートで強制する。`full_allowed`=本文引用可（出典明記必須）。`summary_only`=原文の逐語引用禁止・要約/言い換えのみ。`quote_only`=引用は指定比率以下、かつ著作権法32条の引用要件（主従関係が明確／引用部が明瞭に区別／引用の必然性／出典明示）を満たす構造で出力（BigTechブログ・報道記事はここに分類）。arXivは論文ごとにライセンスが異なるため論文単位で取得し、CC BY-NC-ND のものは図表転載を禁止する分岐を実装する。

> 注: これは設計上のリスク管理であり法的助言ではない。収益化フェーズに入る前に、オーナーは専門家への確認を検討すべき旨を `docs/運用マニュアル.md` に明記する。

## 6. 編集ペルソナ・文体規定

`config/editorial_voice.yaml` に外出しし、オーナーがコードを触らず調整できるようにする。初期値: 一人称・立場は現場の教育関係者（評論家ではない）／禁止表現（「いかがでしたか」「〜と言えるでしょう」「注目が集まっています」等のAI的定型句、生成後に禁止語リストで機械チェック）／必須構造（①何が公開されたか（事実）②現場に何が起きるか（含意）③まだ決まっていないこと（論点）④出典の4部構成）／数字の扱い（原文にない概算・丸め禁止）／立場表明（政策への賛否は論点提示までとし断定的な政治的主張はしない）。

## 7. ネタ選定スコアリング

収集した全情報を配信するのではなく、優先度スコアで絞る。

```
score = 現場インパクト(1-5) × 速報性(1-5) × 議論の余地(1-5)
```

閾値未満は記事化せず、DBに蓄積のみ（後の月次まとめ・L3知見還元で使用）。

## 8. 配信チャネルの制約

- **Web記事**: 自社サイト。完全自動化可能な唯一のチャネル。
- **X**: APIの書き込みは有料プラン前提の可能性が高い。実装前に最新の料金・レート制限を必ず確認する（未確認事項は `docs/ROADMAP.md` に記録）。「API自動投稿」と「下書き生成→承認→手動投稿」の両方を実装し、設定で切替可能にする。
- **note**: 公開された投稿APIが存在しない前提で設計。Markdown下書きを生成→承認→コピペのフローとし、note用の見出し・区切り形式に整形して出力する。
- **YouTube**: 台本と概要欄テキストの生成まで。NotebookLM等での音声化を想定した読み上げやすい文体（漢字の読み仮名、句読点位置）で出力する。

## 9. コスト管理

LLM APIの日次コスト上限を設定し、超過時は自動停止・メール通知する。`make cost` で当月の推定コストを日本語で表示する。
